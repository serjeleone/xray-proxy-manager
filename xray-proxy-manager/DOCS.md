# Xray Proxy Manager — техническая документация

## 1. Назначение

Xray Proxy Manager загружает Xray JSON-subscription, формирует конфигурации выбранных outbound и управляет двумя независимыми Xray-процессами. Один процесс обслуживает активный слот, второй используется для предварительной подготовки следующей конфигурации.

Приложение не определяет способ передачи клиентских соединений в SOCKS5-слоты. Для автоматического изменения активного слота используется совместимый selector API.

## 2. Архитектура

```text
JSON-subscription
  → разбор outbound
  → проверка кандидата
  → резервный Xray-слот
  → переключение selector
  → дренирование прежнего Xray-слота
```

| Слот | Порт по умолчанию | Конфигурация |
|---|---:|---|
| `xray-a` | `10808` | `/config/config.xray-a.json` |
| `xray-b` | `10809` | `/config/config.xray-b.json` |

Все постоянные данные находятся непосредственно в `/config`, который Home Assistant сопоставляет с каталогом конфигурации конкретного приложения. При первом запуске файлы из прежнего `/config/xray-proxy-manager` переносятся в `/config`, если целевые файлы ещё отсутствуют.

## 3. Переключение слотов

При выборе нового outbound выполняются следующие действия:

1. Проверяется, что outbound отличается от текущего активного.
2. Определяется свободный резервный слот.
3. При ручном выборе дренируемый резервный слот принудительно останавливается, если он мешает новой операции.
4. Создаётся отдельная конфигурация Xray для резервного слота.
5. Выполняются `xray -test` и сетевые проверки через SOCKS5 резервного слота.
6. Selector переводится на резервный слот.
7. Прежний активный слот помечается как дренируемый.
8. Новые соединения принимает новый слот; старый процесс продолжает обслуживать уже принятые соединения.
9. Старый слот останавливается после исчезновения отслеживаемых соединений и завершения защитного периода либо по достижении настроенного таймаута.

Открытое транспортное соединение не переносится между процессами. Переключение изменяет только назначение новых соединений.

Автоматический выбор не размещает один и тот же outbound одновременно в `xray-a` и `xray-b`. Если подходящей альтернативы нет, текущая конфигурация сохраняется до следующей проверки.

## 4. Дренирование

Основное условие штатной остановки старого слота:

```text
tracked_connections = 0
AND traffic_counters_are_stable
AND quiet_period_elapsed
```

Верхний блок и карточка соответствующего outbound показывают слот, число оставшихся соединений и кнопку принудительной остановки. Кнопка **«Стоп»** немедленно завершает Xray-процесс дренируемого слота вместе с оставшимися соединениями.

`drain_timeout_minutes` задаёт предельное время ожидания:

- `0` — неограниченное ожидание; соединения не завершаются приложением автоматически;
- `5` — короткий предел для тестовой среды;
- `15…30` — практичный диапазон для обычных клиентских соединений;
- `60` и более — консервативный вариант для длительных сессий.

Безопасное значение зависит от характера соединений. Для максимального сохранения длительных сессий используйте `0`. Независимо от этого таймаута действует защита от явно зависшего последнего соединения: если у дренируемого слота остаётся ровно одно соединение и его outbound получает ошибку или задержку выше `auto_check_max_latency_ms` в `auto_check_failures` последовательных полных проверках, слот принудительно останавливается. Используется тот же общий порог, что и для аварийного failover активного слота.

## 5. Selector API

При `selector_control_enabled: true` приложение обращается к `selector_api_url` и использует `selector_api_secret` как Bearer-токен, если секрет задан.

Selector с именем `selector_tag` должен содержать:

```text
xray-a
xray-b
```

API должно обеспечивать:

- чтение текущего элемента selector;
- выбор `xray-a` или `xray-b`;
- получение списка соединений и цепочки outbound для определения дренирования.

Если selector API недоступно, новое двухслотовое переключение не начинается. Уже работающий Xray-процесс продолжает работу.

## 6. Опциональное управление правилом firewall для OpenWrt

Приложение может через SSH включать или отключать определенную секцию firewall на совместимом узле OpenWrt. Управление выполняется кнопкой play/pause и не изменяет настройки Xray, selector или подписки.

Поддерживаются методы `existing_key`, `generate_key` и `password`. Для режима `generate_key` приложение создаёт ключ в каталоге конфигурации и показывает открытую часть в интерфейсе. Открытый ключ требуется самостоятельно добавить в список разрешённых ключей удалённой системы.

Функция отключается параметром `router_control_enabled: false`.

### Проверки и автоматика

| Параметр | Значения | По умолчанию | Назначение |
|---|---|---|---|
| `auto_checker_enabled` | `true`, `false` | `true` | Включает фоновую стартовую проверку и последующие периодические проверки. Рабочий слот запускается до общей проверки. |
| `auto_switch_best_enabled` | `true`, `false` | `true` | После общей проверки выбирает подходящий outbound с меньшей задержкой. При запуске также учитывает сохранённые успешные измерения и не восстанавливает заведомо более медленный outbound, если улучшение достигает настроенного порога. |
| `auto_switch_excluded_countries` | коды и фрагменты через запятую | `RU` | Исключает outbound из автоматического выбора. Двухбуквенные ISO-коды стран сравниваются точно, остальные элементы — как регистронезависимые фрагменты имени, тега, протокола, адреса и ID. На ручной выбор не влияет. |
| `auto_switch_min_ping_delta_ms` | `0…10000` | `100` | Минимальное улучшение задержки для автоматического переключения. |
| `auto_check_interval_seconds` | `10…86400` | `60` | Интервал «Проверка слота»: проверяется только текущий активный слот, результат сохраняется в общем `latencies.json`. |
| `auto_best_check_interval_seconds` | `60…86400` | `600` | Интервал «Полная проверка»: проверяются все outbound и обновляется общий `latencies.json`; при включённом `auto_switch_best_enabled` затем выбирается лучший вариант. |
| `auto_check_max_latency_ms` | `0…10000` | `500` | Максимальная допустимая минимальная задержка из двух параллельных контрольных запросов. `0` отключает лимит. |
| `auto_check_failures` | `1…100` | `3` | Единый порог последовательных ошибок: запускает аварийный failover активного слота и останавливает дренируемый слот с одним соединением после такого же числа неудачных полных проверок. |
| `auto_check_timeout_seconds` | целое число от `3` | `12` | Таймаут каждого запроса проверки активного слота. |
| `latency_test_timeout_seconds` | целое число от `3` | `12` | Таймаут проверки отдельного outbound. |
| `latency_test_parallelism` | `0…32` | `0` | Максимум одновременно проверяемых outbound. `0` выбирает безопасное значение автоматически: от 2 до 8 с учётом числа CPU и размера списка. |
| `latency_test_url` | URL | `https://www.gstatic.com/generate_204` | Первый контрольный адрес общей пары. Используется при каждой проверке активного, дренируемого или временного слота. |
| `health_check_url` | URL | `https://cp.cloudflare.com/generate_204` | Второй независимый контрольный адрес общей пары. Оба запроса выполняются параллельно; результатом считается минимальная успешная задержка. |

Оба параметра URL образуют одну общую пару и не привязаны к разным видам проверок. Имена ключей сохранены для совместимости с уже установленными конфигурациями. Если в обоих полях сохранён одинаковый адрес, менеджер автоматически добавляет `https://cp.cloudflare.com/generate_204` как второй независимый адрес. Запросы запускаются одновременно; успешного ответа хотя бы от одного адреса достаточно, а отображаемой и сохраняемой задержкой становится минимальный успешный результат.

Пример смешанного фильтра:

```yaml
auto_switch_excluded_countries: "RU, Лучший сервер"
```

`RU` исключает только outbound с кодом страны `RU`. Фрагмент `Лучший сервер` также исключит элемент с именем `Лучший сервер`; регистр символов не учитывается. Текстовые фрагменты должны содержать не менее трёх символов.

### Последовательность запуска

1. Загружаются подписка, состояние и сохранённые результаты latency.
2. Рабочий слот запускается сразу: сначала используется запомненный outbound, при наличии сохранённых измерений он может быть заменён на достаточно более быстрый; `config_index` служит резервным выбором.
3. После запуска рабочего Xray в фоне начинается полная проверка outbound с ограниченным параллелизмом. Прокси продолжает обслуживать трафик во время проверки.
4. После завершения всех проверок выполняется не более одного обычного переключения по правилам минимальной разницы и исключений.
5. Активный слот независимо проверяется каждые `auto_check_interval_seconds`: два HTTP(S)-запроса к `latency_test_url` и `health_check_url` запускаются параллельно. Если успешен хотя бы один, в `latencies.json` записывается минимальная успешная задержка; ошибка фиксируется только при отказе обоих адресов или превышении минимальной задержки `auto_check_max_latency_ms`.
6. После `auto_check_failures` последовательных ошибок запускается аварийный failover: зависший дренируемый standby может быть освобождён, новый слот предварительно проверяется, selector переключается, а старый деградировавший слот сохраняется для отката.
7. После двух успешных проверок нового пути старый деградировавший слот принудительно останавливается, чтобы оставшиеся клиенты переподключились через новый outbound. При двух ошибках нового пути выполняется откат.
8. Полная проверка списка повторяется отдельно каждые `auto_best_check_interval_seconds` независимо от переключателя выбора лучшего сервера; она не задерживает проверку активного слота. Для каждого outbound та же пара контрольных адресов запрашивается параллельно, а в общий результат попадает минимальная успешная задержка. Работающие активный и дренируемый outbound измеряются через их реальные SOCKS-слоты, остальные — через временные процессы. Все результаты обновляют `latencies.json`, а `auto_switch_best_enabled` определяет только необходимость последующего переключения.
9. Если у дренируемого слота остаётся ровно одно соединение и его результат в последовательных полных проверках `auto_check_failures` недоступен или превышает `auto_check_max_latency_ms`, последнее соединение завершается принудительно и слот останавливается. Одиночные ручные тесты в этот счётчик не входят.

При отсутствии сохранённых latency приложение не блокирует запуск и использует запомненный outbound либо `config_index`; результаты стартовой проверки применяются после её завершения.

## 8. Веб-интерфейс

Верхний блок содержит:

- кнопку play/pause для опционального удалённого управления правилом firewall на роутере OpenWrt;
- имя активного outbound;
- протокол, endpoint, outbound tag, активный слот и SOCKS5-порт;
- состояние дренируемого слота и число соединений;
- кнопки проверки, обновления подписки и принудительной остановки.

Карточки outbound показывают оранжевые индикаторы `A` и `B` для работающих слотов. Активный outbound всегда закреплён первой строкой списка и имеет зеленую рамку и градиентную заливку, а дренируемый — непосредственно под ним независимо от выбранной сортировки и фильтров. Карточка дренируемого слота выделяется жёлтой рамкой и градиентной заливкой, всегда получает соответствующую отметку и кнопку **«Стоп»**.

Окно логов поддерживает поиск, перенос строк, переход в начало и конец, копирование в буфер обмена и выгрузку журнала в файл. Имя загружаемого файла определяется средой Home Assistant или браузером.

## 9. Хранение данных

Базовый каталог - /addon_configs/<имя_приложения>/.

| Путь | Назначение |
|---|---|
| `./subscription.json` | Последняя успешно загруженная подписка. |
| `./config.xray-a.json` | Конфигурация `xray-a`. |
| `./config.xray-b.json` | Конфигурация `xray-b`. |
| `./config.last_good.json` | Последняя рабочая конфигурация. |
| `./config.last_good.meta.json` | Метаданные последней рабочей конфигурации. |
| `./state.json` | Активный outbound, слот, задания и ошибки. |
| `./latencies.json` | Результаты проверок. |
| `./runtime-options.json` | Настройки, изменённые в интерфейсе. |
| `./ssh/` | Ключи для опционального удалённого управления OpenWrt. |

Секреты и приватные ключи не выводятся в обычный статус API.

## 10. Восстановление и ограничения

- Если подписка недоступна, используется сохранённая копия.
- Неуспешная новая конфигурация не заменяет последнюю рабочую.
- При неизвестном состоянии selector запускается только запомненный активный слот; одинаковая конфигурация намеренно не запускается во втором слоте.
- При недоступном списке соединений автоматическая остановка дренируемого слота приостанавливается.
- UDP-состояния могут удерживать старый слот дольше TCP.
- Принудительная остановка или истечение `drain_timeout_minutes` может оборвать оставшиеся соединения.
- SOCKS5-порты следует публиковать только в доверенной сети либо защищать аутентификацией.

## 11. CI и релиз

В репозитории используется единый workflow `.github/workflows/build.yml`. Он последовательно выполняет:

1. проверку версии и тега релиза;
2. проверку Python, JavaScript, shell, YAML и JSON;
3. unit-тесты и контроль полноты релизной документации;
4. сборку образов `amd64` и `aarch64`;
5. публикацию multi-arch образа при опубликованном GitHub Release либо при ручном запуске с параметром `publish`.

```text
ghcr.io/serjeleone/xray-proxy-manager:v0.6.6
```
