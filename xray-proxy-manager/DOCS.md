# Xray Proxy Manager — техническая документация

## 1. Назначение

Xray Proxy Manager загружает подписку в формате Xray JSON — готовый набор конфигураций с одним или несколькими outbound, правилами маршрутизации и сопутствующими параметрами. Приложение разбирает такую структуру, выделяет доступные outbound, формирует из них управляемые конфигурации Xray и предоставляет рабочие SOCKS5-слоты с проверкой и переключением. Поддерживаются два режима:

- **однослотовый** — используется только один слот, `xray-a`, а переключение выполняется через перезапуск процесса с разрывом существующих соединений.
- **двухслотовый** — `xray-a` и `xray-b` работают как blue-green пара;

Менеджер предоставляет сетевые точки подключения к Xray и может координировать их с совместимым внешним selector. Клиентский трафик может поступать к слотам напрямую либо через внешний прокси, маршрутизатор или сетевой шлюз. Прозрачная маршрутизация, маркировка пакетов, правила обхода и публикация selector API задаются внешней сетевой конфигурацией.

## 2. Архитектура и режимы

| Слот | Порт по умолчанию | Конфигурация |
|---|---:|---|
| `xray-a` | `10808` | `/config/config.xray-a.json` |
| `xray-b` | `10809` | `/config/config.xray-b.json` |

### Однослотовый режим

```text
создание и xray -test новой конфигурации без остановки текущего процесса
→ остановка xray-a и всех его соединений
→ запуск и проверка xray-a
→ продолжение работы через тот же SOCKS-порт
```

Параллельного рабочего Xray-процесса нет, поэтому происходит кратковременный обрыв. Новая конфигурация формируется и проверяется заранее, пока старый процесс ещё обслуживает трафик.

### Двухслотовый режим

```text
подписка → свободный слот → xray -test → проверка двух URL
          → переключение внешнего selector
          → новый активный слот + дренирование старого
```

Новый outbound заранее запускается в свободном слоте. После переключения selector новые подключения направляются в новый слот. Старый Xray продолжает обслуживать уже установленные соединения до естественного завершения, ручной остановки, аварийного failover или таймаута.

Открытое TCP/UDP-соединение нельзя перенести между процессами или конфигурациями Xray. После разрыва клиент должен создать новое соединение.

## 3. Управление внешним selector и подключение трафика

При `selector_control_enabled: true` приложение обращается к внешнему `selector_api_url` и использует `selector_api_secret` как Bearer-токен, если секрет задан.

Совместимый selector должен содержать точные элементы:

```text
xray-a
xray-b
```

Для автоматического переключения API должно обеспечивать:

- чтение текущего элемента selector;
- выбор `xray-a` или `xray-b`.

Для полной диагностики дренирования желательно также получать список соединений и цепочки использованных outbound.

Если selector API недоступно, новое управляемое двухслотовое переключение не начинается. Уже работающий Xray-процесс продолжает обслуживать трафик.

## 4. Менеджер как источник истины для selector

Сохранённый `active_slot_tag` менеджера является ожидаемым активным слотом. Значение, прочитанное из внешнего selector, не заменяет это состояние, пока ожидаемый Xray-процесс работает.

Пример:

```text
менеджер ожидает xray-b
selector сообщает xray-a
xray-b работает
→ менеджер немедленно записывает xray-b обратно в selector
```

Менеджер принимает значение selector только при одновременном выполнении двух условий:

1. ожидаемый менеджером слот действительно остановлен;
2. слот, сообщённый selector, запущен.

Опрос динамический:

- в обычном состоянии — `selector_status_interval_seconds`, по умолчанию 10 секунд;
- пока слот дренируется — раз в 1 секунду;
- после недоступности API — раз в 1 секунду до восстановления;
- после восстановления API ожидаемый слот принудительно записывается в selector и проверяется повторным GET-запросом.

## 5. Двухслотовое переключение

Обычная операция выполняется в следующем порядке:

1. Менеджер проверяет, что selector соответствует ожидаемому активному слоту.
2. Свободный слот запускается с новой конфигурацией.
3. Выполняются `xray -test` и параллельные запросы к `primary_test_url` и `secondary_test_url`.
4. Selector переключается на новый слот и проверяется чтением текущего значения.
5. Новое состояние записывается в `state.json`.
6. Старый слот переводится в draining и контролируется до остановки.
7. В первые 30 секунд новый слот проверяется повторно; при двух ошибках выполняется rollback.

## 6. Дренирование и диагностика соединений

Дренируемый слот останавливается штатно, когда:

```text
tracked_connections = 0
AND traffic_counters_are_stable
AND drain_quiet_seconds elapsed
AND post-switch protection elapsed
```

Менеджер сопоставляет соединения selector API с `chains`, дополнительно считает живые TCP-сокеты локального SOCKS-порта и выводит на уровне info:

- общее число соединений;
- TCP и UDP отдельно;
- объём трафика;
- число соединений без изменения счётчиков не менее 10 секунд;
- число подключений, появившихся уже после перевода слота в draining.

Сводка пишется при изменении количества соединений и не реже одного раза в 30 секунд. При `log_level: debug` добавляются примеры соединений с ID, исходным адресом, протоколом, назначением, цепочкой outbound и счётчиками байтов.

Новое соединение, обнаруженное в `chains` дренируемого слота, фиксируется отдельным предупреждением. Это позволяет отличить ошибку selector от старой сессии, которая законно продолжает жить после переключения.

`drain_timeout_minutes: 0` оставляет ожидание неограниченным. Кнопка **«Стоп»** немедленно завершает дренируемый процесс. Дополнительно старый слот с одним оставшимся соединением останавливается после числа `auto_check_failures` последовательных полных плохих проверок.

## 7. Проверки outbound

Во всех проверках оба адреса запрашиваются параллельно:

- `primary_test_url`;
- `secondary_test_url`.

Если отвечает хотя бы один адрес, проверка доступности считается успешной и используется меньшая успешная задержка. Если меньшая задержка превышает `auto_check_max_latency_ms`, результат считается деградацией. Ошибка доступности фиксируется только при недоступности обоих адресов.

Проверка активного слота выполняется каждые `auto_check_interval_seconds` и пишется в info-лог вместе с результатами обоих адресов, лучшей задержкой и текущим счётчиком ошибок. Полная проверка всех outbound выполняется отдельно каждые `auto_best_check_interval_seconds`.

После `auto_check_failures` последовательных ошибок активного слота запускается аварийный failover. После двух успешных проверок нового пути старый деградировавший слот принудительно останавливается, чтобы клиенты создали новые соединения.

## 8. Обновление подписки

Подписка обновляется напрямую. Если прямое подключение не удалось, выполняется резервная попытка через уже работающие Xray-слоты: сначала через активный, затем через второй запущенный слот, если он доступен.

После успешной загрузки обновляются сохранённая подписка и список outbound. Изменённая конфигурация активного outbound будет применена при следующем явном выборе outbound или смене режима слотов.

При ошибке используется последняя сохранённая подписка. В UI появляется **«Ошибка синхронизации»** и текст ошибки. Если загруженные данные нельзя разобрать или применить, отображается сообщение: **«Загруженную подписку не удалось применить; предыдущая рабочая подписка сохранена.»**

## 9. Параметры конфигурации

### Подписка и базовые параметры

| Параметр | По умолчанию | Назначение |
|---|---:|---|
| `subscription_url` | пусто | HTTP(S)-адрес JSON-subscription. |
| `config_index` | `0` | Резервный индекс корневой конфигурации подписки. |
| `update_interval_hours` | `1` | Период обновления; `0` отключает расписание. |
| `dual_slot_enabled` | `true` | `true` — blue-green A/B; `false` — только `xray-a` с разрывом соединений при переключении. |
| `log_level` | `warning` | Уровень журнала Xray: `debug`, `info`, `warning`, `error`, `none`. Диагностика менеджера уровня debug также включается этим значением. |
| `user_agent` | `XPM-HA-App` | User-Agent загрузчика подписки. |

### SOCKS5

Для каждого слота задаётся общий TCP/UDP-порт. Приложение использует сеть узла и не публикует отдельные mappings `ports`.

| Параметр | По умолчанию | Назначение |
|---|---:|---|
| `socks_tcp_a` | `10808` | Единый TCP/UDP-порт SOCKS5 `xray-a`. |
| `socks_tcp_b` | `10809` | Единый TCP/UDP-порт SOCKS5 `xray-b`; должен отличаться от A. |
| `proxy_username` | пусто | Имя пользователя SOCKS5; указывается вместе с паролем. Опционально. |
| `proxy_password` | пусто | Пароль SOCKS5; указывается вместе с именем. Опционально. |

### Проверки и автоматический выбор

| Параметр | По умолчанию | Назначение |
|---|---:|---|
| `auto_checker_enabled` | `true` | Включить периодические проверки. |
| `auto_switch_best_enabled` | `true` | После полной проверки выбирать достаточно более быстрый outbound. |

## 10. Веб-интерфейс

Верхний блок содержит:

- имя активного outbound;
- IP-адрес и порт подключения активного слота, а также режим слотов;
- состояние дренируемого слота и число соединений;
- кнопки проверки, смены одно-/двухслотового режима и принудительной остановки текущего дренируемого слота.

Карточки outbound показывают индикаторы `A` и `B` для работающих слотов. Активный outbound закрепляется первым, а дренируемый — сразу под ним независимо от сортировки и фильтров. Окно логов поддерживает поиск, перенос строк, переход в начало и конец, копирование и выгрузку журнала в файл.

## 11. Хранение данных

| Путь | Назначение |
|---|---|
| `/config/subscription.json` | Последняя успешно загруженная подписка. |
| `/config/config.xray-a.json` | Конфигурация `xray-a`. |
| `/config/config.xray-b.json` | Конфигурация `xray-b`. |
| `/config/config.last_good.json` | Последняя рабочая конфигурация. |
| `/config/config.last_good.meta.json` | Метаданные последней рабочей конфигурации. |
| `/config/state.json` | Активный outbound/слот, задания и ошибки. |
| `/config/latencies.json` | Результаты проверок. |
| `/config/runtime-options.json` | Настройки, изменённые из UI. |
| `/config/ssh/` | SSH-ключи удалённого хоста. |
